# Christmas card

`christmas-card/` is an independent Vite entry. The built-in greeting for each language lives in `src/christmas-card/config.js`. The model can be rebuilt using the instructions in `models/christmas-envelope/README.md`. The card renders without external resources.

**Write a card** opens the composer. **Preview** puts its draft in the current fragment and plays the card. **Copy link** and the native share action use a clean page URL with a fragment of the form `#to=...&msg=...&from=...&lang=en|zh`. The WhatsApp button passes that same link to WhatsApp on click. The card reads the fragment in the browser, so the greeting stays out of HTTP requests to the card's origin. Anyone with the link can read the greeting.

The codec applies decoded limits of 40 code points for each name and 240 for up to six message lines. It strips control and bidi formatting characters and ignores a raw fragment over 8,192 characters. A partial greeting uses the built-in recipient and message for missing fields. The sender is omitted when a custom greeting lacks one. Toggling the interface language updates the composer and version button while preserving the words of a shared greeting. Hash changes update the address and letter in place.

The card registers its own service worker with `updateViaCache: 'none'`. It checks for updates on load, when the tab becomes visible, and via **Check for updates**. The worker precaches the HTML, manifest, icons, and Vite dependency closure, including the composer, greeting codec, updater, and GLB. Every card navigation uses the same cached HTML. The installed launch URL opens the built-in greeting.

After precaching succeeds, the worker activates automatically, removes older card caches for its scope, and claims card clients. A failed installation leaves the previous offline card usable. After a takeover, the page waits until the entrance or opening has finished, dialogs are closed, and editable fields have lost focus. It then reloads once with the original URL fragment. The first installation claims the page without reloading it.

Opening or reloading a pre-1.4.0 card online lets the browser discover the fixed worker at the existing script URL. The fixed worker performs a one-time navigation to the new card because legacy pages can miss the takeover. Legacy pages cannot report animation or editor state to that worker. If a pending legacy installation blocks the update queue, fully close the browser and reopen the card online in the same profile. Reloading the page alone leaves the installation stuck.

The gallery worker passes card navigations through and excludes card clients from gallery update coordination. A pre-card gallery worker can return its cached gallery HTML for a card link. The first card-aware upgrade requests activation without user approval after the gallery shell is verified (see the known limitation below). It reopens any card tabs still controlled by the gallery worker and preserves their greeting fragments. Tabs controlled by the card worker keep their documents and editor state. Open gallery documents and active games keep running, and subsequent gallery updates follow the usual approval flow. Offline card support requires one successful online visit and completed card worker installation.

Set the semantic release version in `src/christmas-card/version.js`. Bump the patch for a released fix, the minor for a backward-compatible feature, or the major for a breaking change. The button displays that version and its tooltip shows the generated build hash. The footer gives the version button and update status fixed space so update messages leave the envelope framing stable. `christmas-card/version.json` publishes both as `version` and `build`. The build hash identifies the precache even when the same semantic version is rebuilt.

The deployment selector discovers the GLB through the literal model import. Its cache key is calculated from committed Git-index entries; untracked changes cannot be verified as deployment inputs until added to the index. Publication remains a separate authorized action.

Snow and glowing gold stars accompany the loading status. Warm-up submits hidden draws for the address and trail, cracked seal, flying shards and burst, and final letter. The passes use a small viewport on the normal framebuffer and run on successive animation frames. Parallel shader compilation is used when available. All warm-up waiting shares a 1.5-second deadline. If startup is still pending after 12 seconds in the visible tab, the page displays the HTML greeting. Once ready and visible, the envelope approaches from beyond the left edge, grows in perspective, loops once through a stardust trail, then turns from the address side to the seal and settles. The flight normally takes about three seconds. Playback advances by at most 1/30 second per frame, and the envelope settles automatically after six visible seconds on slow devices. The address shows the greeting recipient. The Open button becomes available after the entrance. Replay restores the settled envelope and its idle camera. Reduced motion keeps the backdrop and loading stars still and skips the flight and animated opening.

The canvas fills the viewport. On resize, the camera computes its shots from fixed bounds for the envelope, flap, letter, and burst. The mobile view pulls back during the final entrance settle while following the same projected path. The camera stays still during idle, then pushes close with a slight tilt as the flap opens. The wide shot reserves room below the header for the complete letter lift and handover.

On tap, golden cracks spread across the wax before its five Blender-authored pieces tumble and shed stardust. The closed seal batches its trim and wax by finish. The warm mouth light combines beams and a soft halo in one baked glow whose mesh follows its silhouette. The entrance trail draws as one point batch. Twinkling gold dust, trailing sparks, and slow snow share a 192-point pool and reuse the trail's shader. Paper uses one shared baked grain tile on the GLB's paper UVs. Metallic trim uses the local Three.js room environment. The renderer caps the pixel ratio at two and limits the backing buffer to 860,000 pixels on detected software renderers.

The letter rises clear of the pocket and flies forward as the envelope recedes. One ivory paper material with subtle baked grain stays visible through the handover. The HTML star becomes visible during the final 240 ms of the approach and reaches full opacity at arrival. The recipient, each line, sender, and Replay follow in order. The opening and reveal fit within 5.5 seconds of animation time. Replay restores the seal, letter, camera, and effects to idle. Reduced motion and the load fallback show the readable HTML card immediately.

The green satin bow and crossing bands lift with the flap. The lower ribbon stays on the front pocket, leaving the address side clear. The moon, snowbanks and illuminated tree use inline SVG and CSS. The moon sits below the header on mobile. The gold-rimmed sleigh crosses it once during the entrance and stays fully visible for 2.32 seconds. Reduced motion skips the crossing and holds the tree lights steady.

Web Audio synthesizes the beat cues and a quiet music-box arrangement of Jingle Bells. A trusted click or keyboard activation unlocks audio. If the first gesture is Tap to Open, the welcome cue plays on that gesture. Mute silences music and effects and saves the choice locally when storage is available. The audio context pauses while the tab is hidden.

After building, run `node scripts/profile-christmas-card.mjs "$LIVE_CARD_URL"` to compare the local build with the live card in the same 1440×900 SwiftShader session. It checks the entrance and the first two seconds of idle and opening against 90% of the reference FPS. The profile reports warm-up draws, worst frame time, draw calls, and shader programs added. It checks for zero new programs in the local build from the first entrance frame through the letter handover. Omit the URL to profile only the local build.

The browser test checks desktop entrance timing in a fresh context with a single late snapshot. It records a full trace in a separate run for the viewport, loop, and opening checks.

Run the upgrade regression with Vite builds of commits `acdd9590` and `6abd140a`, plus the current build. The final argument defaults to `dist`. The test switches the served build on one origin. In the blocked-install case, it starts the later legacy install in a persistent Chromium profile, switches to the current build, and restarts Chromium with the same profile. It opens `christmas-card/index.html` and checks that only the current card cache remains.

```sh
node scripts/test-christmas-card-upgrade.mjs /path/to/acdd9590/dist /path/to/6abd140a/dist dist
```

Known limitation (2026-11-26): with a gallery page still open on a pre-card worker, activation of the new worker was observed to stay pending for at least 120 seconds, so a card link can remain broken until the site's tabs are closed. The cause is not established, and there is no passing automated browser regression for the open-tab and installed-before-visit cases yet.
